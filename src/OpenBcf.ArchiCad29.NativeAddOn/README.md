# OpenBcf.ArchiCad29.NativeAddOn

Native C++ ACAPI Add-On for ArchiCAD 29 - the only client in openBCF that isn't a plain .NET
plugin, because ArchiCAD's Add-On API has no managed hosting story of its own. It does **not**
host .NET in-process - see `Src/HelperProcess.h`'s header comment for why (ArchiCAD cycles
`Initialize`/`FreeData`, effectively a full DLL unload/reload, independently of anything this
Add-On does, which a hosted CoreCLR runtime can't survive). Instead this Add-On launches a
separate, out-of-process `../OpenBcf.ArchiCad29.Helper` and talks to it over two named pipes - see
`Src/HelperProcess.h` for the full protocol, and the main repo `README.md`'s "Why the ArchiCAD
client is different" section for the architecture overview.

## Status: built, deployed, and live-verified against a real ArchiCAD 29 install

Reconciled against the real, freely-downloadable ArchiCAD 29 API DevKit
([github.com/GRAPHISOFT/archicad-api-devkit](https://github.com/GRAPHISOFT/archicad-api-devkit)) -
real function names, struct fields, and two real example Add-Ons (`Selection_Manager` for
menu/selection, `Browser_Control` for the floating-palette pattern), not guessed.

**Real, confirmed-working end to end** on a remote machine with a real ArchiCAD 29 install (see
[[reference_remote_test_machine]] in project memory) - Connect/browse, Create New Issue (including
a captured snapshot), offline `.bcfzip` Export/Import, and the top-level `openBCF` main menu have
all been exercised live, not just compiled.

### Real blockers hit and fixed along the way

- **Compiling at all** took several real fixes: `APIEnvir.h` is a project-local file every DevKit
  example Add-On provides itself (`Src/APIEnvir.h`, copied from `Examples/Selection_Manager`), not
  a DevKit-supplied header; a `constexpr reinterpret_cast` doesn't compile under real MSVC (C2131) -
  use `coreclr_delegates.h`'s own `UNMANAGEDCALLERSONLY_METHOD` macro instead of redefining it (only
  relevant to the now-removed in-process hosting code, kept here as a note in case anything similar
  resurfaces); `IO::fileSystem` (used to delete the temp snapshot render file) needs an explicit
  `#include "FileSystem.hpp"`; it's `nethost.lib`, not `libnethost.lib` (Windows vs. Unix naming) -
  moot now since this project no longer links `nethost.lib` at all (see below).
- **"This add-on cannot be validated. Please contact the distributor."** at ArchiCAD startup - the
  DevKit FAQ (`docs/_f_a_q.html` in the DevKit repo) explains this means the `'MDID'` resource is
  missing or contains a demo/placeholder ID. This project's real Developer ID is `960840751`
  (registered at <https://archicadapi.graphisoft.com>); critically, the **local ID isn't
  developer-assigned** - even a self-picked "real-looking" number fails identically. It must be
  generated by GRAPHISOFT's own system (developer ID + an authorization key), done by registering
  an Add-On entry ("openBCF") in the developer portal, which produced the real local ID
  `4025893662`. Both live in `RFIX/openBCFFix.grc`'s `'MDID'` block.
- **"Your Archicad is not compatible with this Add-On."** even with a valid MDID - the installed
  ArchiCAD build must match the DevKit release's exact version, not just the major version (check
  `ProductVersion.xml` in the ArchiCAD install folder, or `(Get-Item Archicad.exe).VersionInfo`).
- **Linking `nethost.lib` made ArchiCAD reject the Add-On outright**, discovered while this project
  still hosted .NET in-process - the exact mechanism was never fully explained, but removing it
  (by reimplementing hostfxr's own discovery algorithm with plain Win32 calls instead of linking
  the helper library) fixed it. Moot now that this project doesn't host .NET in-process at all, but
  documented here in case a future change reintroduces any `nethost`/`hostfxr` dependency.
- **"Pipe closed while reading a frame" on Create New Issue** - `CaptureSnapshotPng`
  (`AddOnMain.cpp`) uses `ACAPI_Rendering_PhotoRender`, a real photorealistic render, not a cheap
  viewport grab - it reliably exceeds the callbacks pipe's original fixed 5-second response
  timeout on a real project. Fixed by giving that one callback type a much longer (120s) timeout in
  `HelperProcess.cpp` - ArchiCAD still visibly freezes for the render's duration (it runs
  synchronously on ArchiCAD's main thread), just no longer fatally.
- **Export/Import `.bcfzip` hung forever with no visible dialog** - `Microsoft.Win32.SaveFileDialog`/
  `OpenFileDialog` (in `OpenBcf.ArchiCad29.Helper`) need a genuine STA thread, which the helper's
  pipe-handling thread isn't by default; fixed by running the dialog on a dedicated STA thread. A
  second, separate issue then surfaced: the dialog appeared *behind* ArchiCAD's window, since a
  background process has no `SetForegroundWindow` rights for windows it creates - fixed with an
  invisible `Topmost` owner window (a pure z-order flag, not an activation request, so it works
  across processes).
- **The `openBCF` menu was buried under Window ▸ Palettes instead of being its own top-level
  menu** - `RFIX/openBCFFix.grc`'s `'STR#' 32500` resource was always written for a real top-level
  menu (`MenuCode_UserDef`), but `AddOnMain.cpp` registered it under `MenuCode_Palettes` instead
  (a leftover from testing an unrelated, since-disproven bug theory). Reverted to `MenuCode_UserDef`.

Two things remain unverified for a different reason - no DevKit example covers either:

1. **3D camera math** (`GetCamera`/`ApplyCamera` in `AddOnMain.cpp`) - `API_PerspPars`/
   `API_AxonoPars`'s doc comments don't specify axis/sign conventions (roll direction, `viewCone`'s
   axis, the orthographic `API_Tranmat`'s row convention) precisely enough to be certain without a
   live round-trip test.
2. `GetSelectionGuids`/`ApplySelection` round-trip ArchiCAD's own `API_Guid` string format, not the
   compressed IFC GlobalId BCF's `Component.IfcGuid` holds on the other clients (real IFC GlobalId
   access goes through a separate `IFCAPI::` subsystem, confirmed real via `Examples/IFC_Test`, not
   wired up here).

## Build

```powershell
dotnet publish ..\OpenBcf.ArchiCad29.Helper -c Release -r win-x64 --self-contained false
cmake -S . -B build -G "Visual Studio 17 2022" -A x64 `
  -DAC_API_DEVKIT_DIR="C:\Path\To\API-Development-Kit-29"
cmake --build build --config Release
```

`AC_API_DEVKIT_DIR` must point at the extracted DevKit's root (the folder directly containing
`Support/` and `Examples/`), **matched to your installed ArchiCAD's exact build number** (see the
version-mismatch note above) - download the matching `API.Development.Kit.WIN.<version>.zip` from
[the DevKit repo's releases](https://github.com/GRAPHISOFT/archicad-api-devkit/releases).

No .NET SDK / `hostfxr.h` / `coreclr_delegates.h` / `nethost.h` is needed to build this project at
all - it only launches `OpenBcf.ArchiCad29.Helper.exe` as a separate process and talks to it over
named pipes.

The resulting `openBCF.apx` (plus the helper's publish output, copied next to it automatically by
this project's `CMakeLists.txt` post-build step) goes into ArchiCAD's `Add-Ons\Local\` folder
(`C:\Program Files\Graphisoft\Archicad 29\Add-Ons\Local\` by default) flat - same shape as
ArchiCAD's own built-in Local add-ons (Align View, Grid Tool, etc.). ArchiCAD must be closed while
replacing `openBCF.apx` (it locks the file while running); the helper `.exe`/its DLLs only need any
currently-running `OpenBcf.ArchiCad29.Helper.exe` process killed first, not ArchiCAD itself.
